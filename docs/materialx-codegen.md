# MaterialX code generation: the `genglsl_pt` target

Status: design of record. Last revised 2026-09-05.
MaterialX version of record: **1.39.3** — the version inside OpenUSD 26.03,
which hdClaude links and generates with. 1.39.6 differs in header layout,
closure signatures, throughput semantics, and available helpers; see
[implementation-notes.md](implementation-notes.md) for the table.

This document specifies how hdClaude executes MaterialX materials. It is the
implementation of [architecture.md](architecture.md) §1.1: *MaterialX shaders
are compiled and executed, never reinterpreted.*

## 1. What stock MaterialX GLSL generation already gives us

MaterialX 1.39's GLSL generator emits every closure node as a function taking a
`ClosureData` selector. From `libraries/pbrlib/genglsl/lib/mx_closure_type.glsl`:

```glsl
#define CLOSURE_TYPE_DEFAULT      0
#define CLOSURE_TYPE_REFLECTION   1
#define CLOSURE_TYPE_TRANSMISSION 2
#define CLOSURE_TYPE_INDIRECT     3
#define CLOSURE_TYPE_EMISSION     4

struct ClosureData {
    int   closureType;
    vec3  L;
    vec3  V;
    vec3  N;
    vec3  P;
    float occlusion;
};
```

and every BSDF node has the shape

```glsl
void mx_dielectric_bsdf(ClosureData closureData, float weight, vec3 tint,
                        float ior, vec2 roughness, bool retroreflective,
                        float thinfilm_thickness, float thinfilm_ior,
                        vec3 N, vec3 X, int distribution, int scatter_mode,
                        inout BSDF bsdf);
```

This is a substantial gift. The generated material function is already
parameterised by *what we want to ask the closure*, and the whole upstream
pattern graph — `image`, `tiledimage`, every noise, every math and colour node,
every user nodegraph — is generated by MaterialX with no involvement from us.

Two directions map straight onto path-tracer needs:

| Closure type | Path-tracer use |
| --- | --- |
| `CLOSURE_TYPE_REFLECTION` | BSDF evaluation `f(wo, wi)` for next-event estimation |
| `CLOSURE_TYPE_TRANSMISSION` | the transmissive half of the same |
| `CLOSURE_TYPE_EMISSION` | EDF evaluation for emissive surfaces and MIS |

## 2. What is missing, and exactly what we add

Missing: **importance sampling**. Stock `CLOSURE_TYPE_INDIRECT` calls
`mx_environment_radiance`, a prefiltered-environment approximation appropriate
to a rasteriser and useless to a path tracer.

hdClaude adds **one** closure type, which produces **only a direction**:

```glsl
#define CLOSURE_TYPE_PT_SAMPLE  16   // choose an incident direction
```

### Why the density is not the sampler's output

This is the load-bearing decision of the whole target, and the obvious design
is wrong.

MaterialX generates a closure graph by evaluating children *before* the
combinator that consumes them: `mx_mix_bsdf(closureData, BSDF fg, BSDF bg,
float mixValue, out BSDF result)` receives its children already evaluated. So if
`PT_SAMPLE` returned a direction *and* a density, then at combination time
`fg.pdf` and `bg.pdf` would be densities of **two different directions** — each
child's own sample. They cannot be mixed. A `mix` node would have no way to
compute the mixture density its own MIS weight requires, and the natural
mistake is to report the selected child's density instead. That is unbiased-
looking and wrong: it makes every MIS weight in the renderer incorrect, in a way
that survives convergence and cannot be seen by inspecting an image.

The fix is to move the density to the evaluation side. `CLOSURE_TYPE_REFLECTION`
and `CLOSURE_TYPE_TRANSMISSION` are extended to write `BSDF.pdf` alongside
`BSDF.response`, and every combinator mixes densities with exactly the weights
it already mixes responses with. A scattering event becomes:

```text
pass 1   PT_SAMPLE    -> a direction
pass 2   REFLECTION   -> f and pdf, both at that direction
weight = f / pdf
```

and next-event estimation needs only pass 2, which yields its MIS density for
free. One code path produces every density in the renderer, so a combinator
cannot report a density that disagrees with the response beside it.

### The extended structures

`ClosureData` is extended additively: fields the stock implementations read keep
their names and meanings, so unmodified upstream bodies remain valid.

```glsl
struct ClosureData {
    int   closureType;
    vec3  L;              // incident direction
    vec3  V;              // outgoing, toward the viewer
    vec3  N;
    vec3  P;
    float occlusion;

    // --- hdClaude path-tracing extension ---
    vec4  wavelengths;    // the four hero wavelengths, nm
    vec3  u;              // stratified sample: u.xy direction, u.z lobe choice
};
```

```glsl
struct BSDF {
    vec3  response;       // stock: f * cos, or radiance for an EDF
    vec3  throughput;     // stock: energy left for the layer below

    // --- hdClaude path-tracing extension ---
    vec4  spectrum;       // response resolved on the four hero wavelengths
    vec3  sampledL;       // PT_SAMPLE output direction
    float pdf;            // solid-angle density, written by the eval types
    float isDelta;        // specular: skip NEE, MIS weight is one
    vec3  guideAlbedo;    // demodulation albedo for reconstruction guides
    float guideRoughness; // representative roughness for reconstruction guides
};
```

`isDelta` is a `float` rather than a `bool` so the struct's default-value
expression stays a plain aggregate literal (see §5).

Nothing here is a surface-model concept. `guideAlbedo` and `guideRoughness` are
produced *by the closure primitives themselves* — a `conductor_bsdf` knows its
own albedo — never by inspecting a material's name. That is the rule in
[architecture.md](architecture.md) §9.

## 3. Mechanism: a derived target, not a fork

MaterialX's documented extension point for a new render target is a `targetdef`
plus a set of implementation declarations. `essl` derives from `genglsl` this
way (`libraries/targets/essl.mtlx`):

```xml
<targetdef name="essl" inherit="genglsl" />
```

hdClaude does exactly the same:

```xml
<!-- mtlx/targets/genglsl_pt.mtlx -->
<targetdef name="genglsl_pt" inherit="genglsl" />
```

Inheritance means: **every node we do not override is generated by stock
`genglsl`.** We override the `pbrlib` closure nodes and nothing else. The entire
`stdlib` — all pattern, math, colour, and procedural nodes — is untouched
upstream code. That is roughly 95% of the node count and 100% of the surface
area where "approximating" would have been a temptation.

### The override set is exactly 22 files, and is all-or-nothing

MaterialX resolves a source file's `#include` relative to that file's own
directory. So an upstream `pbrlib/genglsl/mx_dielectric_bsdf.glsl` resolves
`lib/mx_closure_type.glsl` to *upstream's* copy, not hdClaude's — and if one
upstream closure is generated beside one hdClaude closure, both copies are
emitted and `struct ClosureData` is declared twice. That is a compile error,
which is the right failure mode, but it means the override set cannot be
partial at runtime.

The set is exactly the pbrlib GLSL files that include `lib/mx_closure_type.glsl`.
In MaterialX 1.39 that is **22 files**, enumerated in
`mtlx/pbrlib/genglsl_pt/hdclaude_pbrlib_impl.mtlx`. Verified against the 1.39.6
source: **no `stdlib` file includes it**, which is what makes the boundary clean
and the inheritance safe.

Files:

```text
mtlx/
  targets/genglsl_pt.mtlx                  targetdef
  pbrlib/genglsl_pt/
    hdclaude_pbrlib_impl.mtlx              implementation declarations
    mx_dielectric_bsdf.glsl                sample/pdf added to the stock body
    mx_conductor_bsdf.glsl
    mx_generalized_schlick_bsdf.glsl
    mx_oren_nayar_diffuse_bsdf.glsl
    mx_burley_diffuse_bsdf.glsl
    mx_translucent_bsdf.glsl
    mx_subsurface_bsdf.glsl
    mx_sheen_bsdf.glsl
    mx_chiang_hair_bsdf.glsl
    mx_layer_bsdf.glsl                     stochastic layer selection
    mx_mix_bsdf.glsl                       weighted lobe selection
    mx_add_bsdf.glsl                       equal-probability lobe selection
    mx_multiply_bsdf_*.glsl
    mx_uniform_edf.glsl  mx_*_edf.glsl
    mx_anisotropic_vdf.glsl
    lib/
      mx_closure_type.glsl                 the extended ClosureData / BSDF
      mx_pt_sampling.glsl                  shared sampling helpers
      mx_pt_spectral.glsl                  RGB -> hero-wavelength upsampling
```

Each override starts as the upstream body verbatim, with `PT_SAMPLE` and
`PT_PDF` branches appended. Keeping the evaluation branches byte-identical to
upstream is deliberate: it makes divergence from MaterialX visible in a diff,
and it makes upstream MaterialX upgrades a mechanical merge.

## 4. The combinators are the hard part

`layer`, `mix`, `add`, and `multiply` are where a naive implementation silently
becomes wrong, because sampling does not distribute over them the way evaluation
does. With the protocol in §2 each one has two jobs: select a direction under
`PT_SAMPLE`, and combine densities under evaluation.

- **`mix(fg, bg, w)`** — evaluation is `w*fg + (1-w)*bg`. Selection takes `fg`
  with probability `w`; the density is the *mixture* `mix(bg.pdf, fg.pdf, w)`,
  which is available because both children were evaluated at the same
  direction.
- **`add(a, b)`** — responses add, but densities do not: a density must
  integrate to one, so the lobes form an equal-weight mixture
  `0.5*(pdf_a + pdf_b)` and selection is uniform.
- **`layer(top, base)`** — the stock implementation threads `top.throughput`
  into the base, and `throughput` is exactly `1 - directional_albedo(top)`. So
  the probability of interacting with the top layer is
  `p = 1 - average(top.throughput)`, already present and requiring no new
  computation. Selection uses `p`; the density is `mix(base.pdf, top.pdf, p)`.
  `p` is clamped away from both endpoints, so a lobe can never be selected with
  zero probability while still contributing to the response — which would be an
  infinite weight.
- **`multiply(bsdf, scalar|color)`** — scales the response and leaves the
  direction distribution alone, so the density passes through untouched.
  Scaling it too would be a double count that a furnace test at a single weight
  would not reveal.

Under evaluation, a combined closure is delta only if *every* constituent lobe
is; under sampling, only if the branch actually taken is. A mix of a mirror and
a diffuse lobe is not a delta closure, and treating it as one would suppress
next-event estimation on the diffuse half.

## 5. The generator

Three C++ extension points, all of them existing MaterialX mechanisms with an
upstream precedent, verified against the 1.39.6 source.

**1. The `BSDF` struct comes from the Syntax, not from a library file.**
`GlslSyntax.cpp` registers it as a type syntax:

```cpp
registerTypeSyntax(Type::BSDF, std::make_shared<AggregateTypeSyntax>(
    this, "BSDF", "BSDF(vec3(0.0),vec3(1.0))", EMPTY_STRING, EMPTY_STRING,
    "struct BSDF { vec3 response; vec3 throughput; };"));
```

`hdclaude::PathTracerSyntax : public MaterialX::VkSyntax` re-registers
`Type::BSDF` with the extended definition and a matching default-value
expression. Both strings come from the same registration, so they cannot drift
apart. This is why `isDelta` is a `float`: the default value must stay a plain
aggregate literal.

**2. The `ClosureData` constructor is a token substitution.** The generated
`makeClosureData` body is the `$closureDataConstructor` token, substituted by
the generator. `MslShaderGenerator` already overrides it
(`_tokenSubstitutions[HW::T_CLOSURE_DATA_CONSTRUCTOR] = "{closureType, L, V, N, P, occlusion}"`),
and hdClaude does the same for its extended field list. A mismatch between the
struct and the substitution is a compile error rather than a silent
miscompile — the desired failure mode.

**3. The `surface` node's calling convention.** `ClosureData` is constructed
not by the closures but by the **`surface` node**, in
`MaterialXGenHw/Nodes/HwSurfaceNode.cpp` — and that construction encodes a
rasteriser: the `REFLECTION` case sits inside a loop over `u_lightData`, and the
`INDIRECT` case calls the prefiltered environment. Neither is meaningful to a
path tracer, which supplies its own direction and its own light sample.

hdClaude therefore adds `PathTracerSurfaceNode`, a C++ node implementation
registered by the generator and declared as
`<implementation nodedef="ND_surface" target="genglsl_pt"/>`. It emits a body
calling the BSDF and EDF with the **caller-supplied** `closureData`: no light
loop, no environment lookup. The stock `surface` implementation is likewise
bodiless in XML and entirely C++, so this follows the same shape.

The closure overrides supply *sampling*; this supplies the **calling
convention**. Both are needed, and this one is the smaller and less obvious of
the two.

**4. The generator itself.**
`hdclaude::PathTracerShaderGenerator : public MaterialX::VkShaderGenerator`
overrides target identity and emission:

- `getTarget()` returns `genglsl_pt`.
- Emits a **compute** stage, not vertex/fragment. Geometric inputs
  (`normal`, `tangent`, `texcoord`, `position`, `geomprop_*`) that stock
  generation binds as vertex-stage inputs are instead resolved from an
  interpolated `SurfaceHit` struct the wavefront `shade` kernel fills in.
  This is done by supplying a custom `HwImplementation` for the geometric
  node set, which is the same mechanism the MSL and ESSL generators use to
  redirect stage inputs.
- Emits the hdClaude material ABI entry points:

```glsl
void hdclaude_material_shade(inout ClosureData cd, in SurfaceHit hit, inout BSDF bsdf);
void hdclaude_material_displace(in SurfaceHit hit, out vec3 offset);
```

The struct's members are whatever geometry the material reads, so the generator
also emits the function that fills it:

```glsl
void hdclaude_set_surface_hit(vec3 P, vec3 N, vec3 T,
                              vec3 Pobj, vec3 Nobj, vec3 Tobj, vec2 uv);
```

**Every member is assigned.** The struct is a global, so a member the setter
skips is not "left for the kernel to fill" — nothing else fills it, and the
material reads an undefined value. A member with no argument to take, such as a
primvar the mesh adapter does not carry, is assigned its type's zero. This was
found the hard way: the object-space position was skipped, so every material
with a 3D procedural node — `fractal3d`, `noise3d`, `worleynoise3d`, anything
authored in object space — shaded from undefined memory and rendered black.

- Uniform/sampler binding follows `VkResourceBindingContext` with hdClaude's
  fixed descriptor-set assignment: set 0 renderer-global, set 1 scene,
  **set 2 material** (the generated block), set 3 textures (partially bound
  descriptor-indexed array).

Textures are the one place the generator is adapted rather than reused
verbatim: MaterialX emits `sampler2D` uniforms per image node, and hdClaude
rewrites those into indices into the bindless array so that one compiled
program serves every instance of a material variant. The rewrite happens on the
*reflected* uniform block, not on the graph, so it cannot change shading
semantics.

## 6. Compilation and caching

1. Build a MaterialX document from the composed Hydra material network using
   public `UsdMtlx`/`HdMaterialNetwork` data.
2. Generate GLSL with `PathTracerShaderGenerator` for target `genglsl_pt`.
3. Compile to SPIR-V with glslang, pinned to the same Khronos SDK release as
   the headers and loader. Target Vulkan 1.3 / SPIR-V 1.6.
4. Cache under a SHA-256 key covering: generated source, MaterialX version,
   glslang version, target, SPIR-V version, optimisation mode, and the hdClaude
   material ABI version. Any ABI change invalidates every entry by construction.
5. Specialise the `shade` pipeline per material and record it in the per-material
   dispatch table.

A material that fails at any step is **rejected with a diagnostic naming the
prim, the MaterialX node, and the compiler message**. It is not silently
replaced by an approximation. Unbound geometry — genuinely no material — uses
Hydra `displayColor` through a small generated MaterialX document, so even the
fallback goes through the same pipeline.

## 7. Known upstream friction

- **1.39.3 Vulkan generator stage-connector prefix.** The version inside
  OpenUSD 26.03 emits individually located stage connector variables while
  retaining the desktop-GLSL `vd.` instance prefix in expressions. Because
  hdClaude generates a *compute* stage with no vertex/fragment connector block,
  this defect is bypassed rather than worked around. Recorded here so the
  absence of a compatibility shim is not mistaken for an oversight.
- **`ClosureData` construction** is emitted through the `$closureDataConstructor`
  substitution. Extending the struct requires the generator to extend that
  substitution in lockstep; a mismatch is a compile error, not a silent
  miscompile, which is the desired failure mode.

## 8. Acceptance

The target is accepted when, on the gallery:

1. Every MaterialX material in the gallery scenes compiles, with zero materials
   in a fallback or approximated state.
2. A white-furnace test on `oren_nayar_diffuse_bsdf`, `burley_diffuse_bsdf`,
   `dielectric_bsdf`, `conductor_bsdf`, `generalized_schlick_bsdf`,
   `sheen_bsdf`, `translucent_bsdf`, and all four combinators integrates to
   within 0.5% of the analytic directional albedo.
3. A chi-squared test confirms each closure's `PT_SAMPLE` direction
   distribution matches the density its evaluation branch reports, at a set of
   representative parameter points.
4. For every closure **and every combinator**, the density reported at a
   `PT_SAMPLE`-produced direction is finite and nonzero. A combinator that
   reports a zero density for a direction one of its lobes can produce is an
   infinite path weight.
5. For every closure and combinator, the reported density integrated over the
   sphere **plus** the probability of sampling a direction the closure reports
   zero density for comes to one.

   The second term is not slack. A visible-normal sampler can reflect about a
   microfacet tilted far enough that the result falls below the horizon, where
   the closure cannot scatter; those samples are discarded with weight zero and
   the estimator stays unbiased, but their probability mass is missing from the
   integral. At roughness 0.8 that is 37% of samples, so the bare integral is
   0.62 and entirely correct. See
   [implementation-notes.md](implementation-notes.md).

   This is still the test that catches the §4 mistake: a combinator returning
   the selected child's density instead of the mixture passes items 2 and 3 and
   fails this one.

Items 2-5 are unit tests that run without a scene and without OpenUSD, and they
gate every change to this target.

Each is checked to contain hdClaude's ABI entry point and the surface override's

hdClaude contains no knowledge of the names `standard_surface` or
`open_pbr_surface` anywhere. They arrive as ordinary nodegraphs over the 22
overridden closures, which is the whole of the claim in
[architecture.md](architecture.md) §1.1.

What remains of the numerical acceptance in §8 is item 2 as written: each
furnace compared with its analytic directional albedo to 0.5%, rather than
bounded above.

Item 3 is `tests/closure_chi2.comp.glsl` and `MeasureDistribution` in
`tests/closure_validation_tests.cpp`. Each closure's sampled directions are
histogrammed over 20 x 40 cells of the sphere against its reported density
integrated over each cell by 24 x 24 quadrature, evaluated the way `shade`
evaluates -- REFLECTION in front of the normal, TRANSMISSION behind -- and
Pearson's statistic is tested at one per cent across the set. It also asserts
the probability mass from the same quadrature, and that a closure keeps most of
what it samples, so that a closure discarding everything cannot agree with
itself. It found four defects on its first runs, each recorded in the
[roadmap](roadmap.md) decision log: rough dielectric and generalized-Schlick
transmission reporting density for back-facing microfacets; both closures'
reflection samples leaving below the horizon and being weighted as
transmission; and `chiang_hair_bsdf` and `translucent_bsdf` answering only
REFLECTION, so that the integrator discarded every sample behind the normal.

Generation cannot succeed until all 22 overrides are present, for the reason in
§3. Tracked as phase 4 in [roadmap.md](roadmap.md).
