# MaterialX code generation: the `genglsl_pt` target

Status: design of record. Last revised 2026-09-05.
MaterialX version of record: **1.39** (1.39.3 ships inside OpenUSD 26.03;
1.39.6 is the upstream checkout used as the reference for this design).

This document specifies how hdClaude executes MaterialX materials. It is the
implementation of [architecture.md](architecture.md) §1.1: *MaterialX shaders
are compiled and executed, never reinterpreted.*

## 1. What stock MaterialX GLSL generation already gives us

MaterialX 1.39's GLSL generator emits every closure node as a function taking a
`ClosureData` selector. From `libraries/pbrlib/genglsl/lib/mx_closure_type.glsl`:

```glsl
#define CLOSURE_TYPE_DEFAULT      0
#define CLOSURE_TYPE_REFLECTION   1
#define CLOSURE_TYPE_TRANSMISSION 2
#define CLOSURE_TYPE_INDIRECT     3
#define CLOSURE_TYPE_EMISSION     4

struct ClosureData {
    int   closureType;
    vec3  L;
    vec3  V;
    vec3  N;
    vec3  P;
    float occlusion;
};
```

and every BSDF node has the shape

```glsl
void mx_dielectric_bsdf(ClosureData closureData, float weight, vec3 tint,
                        float ior, vec2 roughness, bool retroreflective,
                        float thinfilm_thickness, float thinfilm_ior,
                        vec3 N, vec3 X, int distribution, int scatter_mode,
                        inout BSDF bsdf);
```

This is a substantial gift. The generated material function is already
parameterised by *what we want to ask the closure*, and the whole upstream
pattern graph — `image`, `tiledimage`, every noise, every math and colour node,
every user nodegraph — is generated by MaterialX with no involvement from us.

Two directions map straight onto path-tracer needs:

| Closure type | Path-tracer use |
| --- | --- |
| `CLOSURE_TYPE_REFLECTION` | BSDF evaluation `f(wo, wi)` for next-event estimation |
| `CLOSURE_TYPE_TRANSMISSION` | the transmissive half of the same |
| `CLOSURE_TYPE_EMISSION` | EDF evaluation for emissive surfaces and MIS |

## 2. What is missing, and exactly what we add

Missing: **importance sampling** and **PDF evaluation**. Stock
`CLOSURE_TYPE_INDIRECT` calls `mx_environment_radiance`, a prefiltered-environment
approximation appropriate to a rasteriser and useless to a path tracer.

hdClaude adds two closure types and the data they need:

```glsl
#define CLOSURE_TYPE_PT_SAMPLE  16   // choose a direction; return weight and pdf
#define CLOSURE_TYPE_PT_PDF     17   // pdf of a given direction, for MIS
```

`ClosureData` is extended with the fields those types consume and produce.
The extension is *additive*: fields the stock implementations read keep their
names and meanings, so the unmodified upstream `mx_*.glsl` bodies remain valid
for the evaluation types.

```glsl
struct ClosureData {
    int   closureType;
    vec3  L;              // incident direction (eval/pdf in, sample out)
    vec3  V;              // outgoing (toward viewer)
    vec3  N;
    vec3  P;
    float occlusion;

    // --- hdClaude path-tracing extension ---
    vec4  wavelengths;    // the four hero wavelengths, nm
    vec3  u;              // stratified sample: u.xy direction, u.z lobe choice
    float lobePdf;        // discrete lobe-selection probability, accumulated
};
```

and `BSDF` is extended to carry the sampling result and the MIS/guide data the
integrator and DLSS need:

```glsl
struct BSDF {
    vec3  response;       // stock: f * cos, or radiance for EDF
    vec3  throughput;     // stock: energy left for the layer below

    // --- hdClaude path-tracing extension ---
    vec4  spectrum;       // response resolved on the four hero wavelengths
    float pdf;            // solid-angle pdf of `L`
    bool  isDelta;        // specular; NEE must be skipped, MIS weight is 1
    vec3  guideAlbedo;    // demodulation albedo for reconstruction guides
    float guideRoughness; // representative roughness for reconstruction guides
};
```

Nothing here is a surface-model concept. `guideAlbedo` and `guideRoughness` are
produced *by the closure primitives themselves* — a `conductor_bsdf` knows its
own albedo — never by inspecting a material's name. That is the rule in
[architecture.md](architecture.md) §9.

## 3. Mechanism: a derived target, not a fork

MaterialX's documented extension point for a new render target is a `targetdef`
plus a set of implementation declarations. `essl` derives from `genglsl` this
way (`libraries/targets/essl.mtlx`):

```xml
<targetdef name="essl" inherit="genglsl" />
```

hdClaude does exactly the same:

```xml
<!-- mtlx/targets/genglsl_pt.mtlx -->
<targetdef name="genglsl_pt" inherit="genglsl" />
```

Inheritance means: **every node we do not override is generated by stock
`genglsl`.** We override the `pbrlib` closure nodes and nothing else. The entire
`stdlib` — all pattern, math, colour, and procedural nodes — is untouched
upstream code. That is roughly 95% of the node count and 100% of the surface
area where "approximating" would have been a temptation.

Files:

```text
mtlx/
  targets/genglsl_pt.mtlx                  targetdef
  pbrlib/genglsl_pt/
    hdclaude_pbrlib_impl.mtlx              implementation declarations
    mx_dielectric_bsdf.glsl                sample/pdf added to the stock body
    mx_conductor_bsdf.glsl
    mx_generalized_schlick_bsdf.glsl
    mx_oren_nayar_diffuse_bsdf.glsl
    mx_burley_diffuse_bsdf.glsl
    mx_translucent_bsdf.glsl
    mx_subsurface_bsdf.glsl
    mx_sheen_bsdf.glsl
    mx_chiang_hair_bsdf.glsl
    mx_layer_bsdf.glsl                     stochastic layer selection
    mx_mix_bsdf.glsl                       weighted lobe selection
    mx_add_bsdf.glsl                       equal-probability lobe selection
    mx_multiply_bsdf_*.glsl
    mx_uniform_edf.glsl  mx_*_edf.glsl
    mx_anisotropic_vdf.glsl
    lib/
      mx_closure_type.glsl                 the extended ClosureData / BSDF
      mx_pt_sampling.glsl                  shared sampling helpers
      mx_pt_spectral.glsl                  RGB -> hero-wavelength upsampling
```

Each override starts as the upstream body verbatim, with `PT_SAMPLE` and
`PT_PDF` branches appended. Keeping the evaluation branches byte-identical to
upstream is deliberate: it makes divergence from MaterialX visible in a diff,
and it makes upstream MaterialX upgrades a mechanical merge.

## 4. The combinators are the hard part

`layer`, `mix`, `add`, and `multiply` are where a naive implementation silently
becomes wrong, because sampling does not distribute over them the way evaluation
does.

- **`mix(fg, bg, w)`** — evaluation is `w*fg + (1-w)*bg`. Sampling selects `fg`
  with probability `w`, and the returned pdf must be the *mixture* pdf
  `w*pdf_fg + (1-w)*pdf_bg`, not the selected lobe's pdf. Getting this wrong
  produces an image that is subtly and unfixably wrong under MIS.
- **`add(a, b)`** — no authored weights. Select with equal probability, return
  the mixture pdf `0.5*pdf_a + 0.5*pdf_b`.
- **`layer(top, base)`** — the stock implementation threads `bsdf.throughput`
  from the top layer into the base. Sampling uses one-sample stochastic
  selection with the *directional albedo* of the top layer as its probability,
  which is precisely what `throughput` already encodes; the base is then
  weighted by `throughput / (1 - p)`.
- **`multiply(bsdf, scalar|color)`** — does not change the direction
  distribution; scales weight and leaves pdf alone.

Each combinator therefore needs, in the `PT_PDF` direction, to evaluate *all*
its children (not just the selected one). This is why `PT_PDF` is a separate
closure type rather than a byproduct of `PT_SAMPLE`.

## 5. The generator

`hdclaude::PathTracerShaderGenerator : public MaterialX::VkShaderGenerator`
overrides target identity and emission:

- `getTarget()` returns `genglsl_pt`.
- Emits a **compute** stage, not vertex/fragment. Geometric inputs
  (`normal`, `tangent`, `texcoord`, `position`, `geomprop_*`) that stock
  generation binds as vertex-stage inputs are instead resolved from an
  interpolated `SurfaceHit` struct the wavefront `shade` kernel fills in.
  This is done by supplying a custom `HwImplementation` for the geometric
  node set, which is the same mechanism the MSL and ESSL generators use to
  redirect stage inputs.
- Emits the hdClaude material ABI entry points:

```glsl
void hdclaude_material_shade(inout ClosureData cd, in SurfaceHit hit, inout BSDF bsdf);
void hdclaude_material_displace(in SurfaceHit hit, out vec3 offset);
```

- Uniform/sampler binding follows `VkResourceBindingContext` with hdClaude's
  fixed descriptor-set assignment: set 0 renderer-global, set 1 scene,
  **set 2 material** (the generated block), set 3 textures (partially bound
  descriptor-indexed array).

Textures are the one place the generator is adapted rather than reused
verbatim: MaterialX emits `sampler2D` uniforms per image node, and hdClaude
rewrites those into indices into the bindless array so that one compiled
program serves every instance of a material variant. The rewrite happens on the
*reflected* uniform block, not on the graph, so it cannot change shading
semantics.

## 6. Compilation and caching

1. Build a MaterialX document from the composed Hydra material network using
   public `UsdMtlx`/`HdMaterialNetwork` data.
2. Generate GLSL with `PathTracerShaderGenerator` for target `genglsl_pt`.
3. Compile to SPIR-V with glslang, pinned to the same Khronos SDK release as
   the headers and loader. Target Vulkan 1.3 / SPIR-V 1.6.
4. Cache under a SHA-256 key covering: generated source, MaterialX version,
   glslang version, target, SPIR-V version, optimisation mode, and the hdClaude
   material ABI version. Any ABI change invalidates every entry by construction.
5. Specialise the `shade` pipeline per material and record it in the per-material
   dispatch table.

A material that fails at any step is **rejected with a diagnostic naming the
prim, the MaterialX node, and the compiler message**. It is not silently
replaced by an approximation. Unbound geometry — genuinely no material — uses
Hydra `displayColor` through a small generated MaterialX document, so even the
fallback goes through the same pipeline.

## 7. Known upstream friction

- **1.39.3 Vulkan generator stage-connector prefix.** The version inside
  OpenUSD 26.03 emits individually located stage connector variables while
  retaining the desktop-GLSL `vd.` instance prefix in expressions. Because
  hdClaude generates a *compute* stage with no vertex/fragment connector block,
  this defect is bypassed rather than worked around. Recorded here so the
  absence of a compatibility shim is not mistaken for an oversight.
- **`ClosureData` construction** is emitted through the `$closureDataConstructor`
  substitution. Extending the struct requires the generator to extend that
  substitution in lockstep; a mismatch is a compile error, not a silent
  miscompile, which is the desired failure mode.

## 8. Acceptance

The target is accepted when, on the gallery:

1. Every MaterialX material in the gallery scenes compiles, with zero materials
   in a fallback or approximated state.
2. A white-furnace test on `oren_nayar_diffuse_bsdf`, `dielectric_bsdf`,
   `conductor_bsdf`, `generalized_schlick_bsdf`, `sheen_bsdf`, and the four
   combinators integrates to within 0.5% of the analytic directional albedo.
3. A chi-squared test confirms each closure's `PT_SAMPLE` distribution matches
   its `PT_PDF` at a set of representative parameter points.
4. `PT_PDF` of a `PT_SAMPLE`-produced direction agrees with the pdf returned by
   the sample, for every closure and combinator.

Items 2-4 are unit tests that run without a scene and without OpenUSD, and they
gate every change to this target.
